durable-request /compact mapping

把 chat 里的 /compact 封装成 durable-request 里的 /compact 选项

用户在 chat 输入 /compact，与用户在 durable-request checkpoint 里选择 /compact，本质上都是同一个宿主意图：请求上下文压缩或会话整理。
durable-request 真正新增的价值，不是创造新的 compact 能力，而是把这个宿主动作包装成一个更稳定的协议入口，并提前把 payload、保留策略、fallback 路径、恢复摘要一起设定好。

当前结论基于：Copilot changelog / SDK bundle、Cursor hooks docs / prompting docs / forum 里关于 /summarize 与 manual compaction 的证据、当前 agent 可见工具边界。

One-line verdict

一句话结论

  • Copilot IDE (VS Code)：/compact 作为 host slash command 已被明确看到，durable-request 可以把它包装成 protocol wrapper。
  • Cursor IDE：更像是把 durable-request 的 /compact 映射到 host /summarize，而不是 literal /compact；manual compaction 已有证据，但程序化触发链仍需验证。
  • 两边都可以把 /compact 选项做成“自动带策略”的入口，但真正的 host compaction 是否能被 agent 稳定直接触发，当前 Copilot 侧仍偏内部 plumbing，Cursor 侧则更像 stop -> /summarize 的候选链。

What durable-request adds

durable-request 额外做什么

  • 预设 payload：比如只保留 goals、recent decisions、active TODO、next action。
  • 预设策略：比如 hard compact 优先，失败则回落到 soft handoff。
  • 预设恢复路径：比如自动生成 handoff summary，再把 resume 指令注回下一轮。

Three follow-ups

三个补充问题

Q1

Cursor 的 soft compact / handoff 和 hard compact，差别到底在哪里？

hard compact 是宿主原生压缩：同一个 session 不变，宿主在内部对长上下文做裁剪、总结或重排，agent 继续留在原来的会话轨道里。 它的关键特征不是“有 summary”，而是 会话身份、宿主内部上下文管理、可能的缓存路径和隐藏状态都尽量不换轨。

soft compact / handoff 则是 agent 自己显式写一个交接包：把目标、已决策内容、TODO、下一步、协议要求整理出来，再由新一轮对话或恢复逻辑重新加载。 它的关键特征不是“压缩算法”，而是 用显式文档替代宿主内部状态。

在 Cursor 当前 durable-request 实现里，稳定可控的是 soft compact / handoff，因为现有证据链仍然落在 checkpoint.sh、checkpoint-ui.sh、steering-hook.sh 这些 shell / tmux / stdout 注入通道上； 还没有证据表明当前就能稳定直达宿主 hard compact backend。

Q2

从 cache 友好角度，哪种 compact 最好？

No.1
host hard compact。
这是最 cache-friendly 的形态，因为它最有机会保持原有 session continuity，由宿主在内部做 compaction，而不是把一大段新 summary 重新拼进 prompt。
No.2
结构化 soft compact。
如果没有 hard compact，次优方案不是长篇 prose handoff，而是一个字段固定、顺序固定、长度受控的 compact capsule，例如：goals / decisions / active todo / next action / protocol state。 这种格式对 prompt cache 更友好，因为稳定前缀更容易重复命中。
No.3
自由文本 handoff。
这是最不 cache-friendly 的方式，因为每次 compact 后文本表述都会大幅波动，前缀不稳定，token churn 高，而且更容易把协议要求埋在自然语言里。
如果你关心 cache，不要把 compact 做成“自动写一大段总结”。更稳的 portable 策略是：稳定协议前缀 + 小而固定的结构化 handoff payload。

Q3

compact 容易让 agent 忘掉 durable-request 协议，怎么防止它中途跳出？

关键点是：不能只依赖文档 handoff。如果 durable-request 协议只存在于“上一轮对话记忆”或“这次 summary 文案”里，那 compact 之后它就最容易被弱化、截断或遗漏。

更稳的做法是把 compact payload 分成三层：

Layer 1
Protocol capsule：durable-request 的关键行为约束，用短、小、版本化、固定字段的格式保存，例如 must_checkpoint=true、checkpoint_style=cursor-cli、pending_checkpoint=false、resume_mode=handoff。
Layer 2
Task handoff：当前任务状态本身，例如目标、已完成内容、未决问题、下一步和必要文件。
Layer 3
Re-entry guard：compact 后第一次恢复时，外部机制必须把 protocol capsule 再显式注入一遍，而不是赌模型自己记得。对于 Cursor，这个 guard 最自然的落点就是 hook / shell 注入；对于 Copilot，则更适合作为 customization / wrapper 层的固定恢复动作。
所以答案不是“只通过 handoff 文档”，而是 文档 handoff + 协议 sidecar + post-compact rehydrate。 如果现在把 compact 变成用户显式可触发动作，最稳的实现不是让 compact 自己“顺便带一段自然语言提醒”，而是让 wrapper 自动附带一个 稳定、短、机器友好的 durable-request protocol capsule，并在 compact 后首次恢复时强制再注回去。

Boundary

仍然要保守表述的部分

  • Copilot SDK 里能看到 compactionControl、compact_20260112 和 toolRunner()，但这更像内部 plumbing，而不是稳定公开 agent API。
  • 没有公开证据表明 durable-request 当前就能在 Cursor 里直接 dispatch literal /compact；更像的宿主入口是 /summarize。
  • stop.followup_message="/summarize" 是高价值候选链，但还没拿到“auto-submitted followup 一定走 slash parser”这一步的硬证据。
  • “Reset Context” 在论坛里也被提到，但语义和稳定性仍然模糊，不能先拿它当自动化 target。
  • 因此产品表达最好不要写成“durable-request 新增 compact 能力”，而要写成“durable-request 提供 compact wrapper / orchestration layer”。
建议最终措辞： durable-request 里的 /compact 不应被描述成一个新的压缩能力；它更准确的定位是 宿主 compact 的协议包装层。 在 Copilot IDE，它可以优先映射到真实 host /compact；在 Cursor IDE，它当前应先映射到 host /summarize wrapper，并用 stop / preCompact / Rules / sidecar 去补足协议与恢复逻辑；如果这条链不稳定，再回退到 policy-driven soft compact。
