# Steering 用户体验对比分析

## 概述

本文档对比两种 steering 实现方案的用户体验，以确定最佳实现路径。

## 方案对比

### 方案 A: CLI (`steer` 命令)

**用户流程:**

```
1. Agent 正在运行某个任务
2. 用户想要发送 steering message
3. 用户切换到另一个终端窗口（或打开新终端）
4. 用户输入: steer "focus on the API layer"
5. 终端显示: [steer] Queued: focus on the API layer
6. 用户切换回 Cursor 窗口
7. 下次工具调用时，agent 看到 steering message
```

**认知负担:**
- 需要记住 `steer` 命令存在
- 需要记住命令语法
- 需要管理多个窗口

### 方案 B: 扩展 (状态栏按钮)

**用户流程:**

```
1. Agent 正在运行某个任务
2. 用户想要发送 steering message
3. 用户点击状态栏 [🔊 Steer] 按钮（或按 Ctrl+Shift+S）
4. 输入框弹出，用户输入: focus on the API layer
5. 按 Enter 确认
6. 通知显示: ⚡ Steering queued: "focus on the API layer"
7. 状态栏按钮短暂变色表示有 pending steering
8. 下次工具调用时，agent 看到 steering message
```

**认知负担:**
- 状态栏按钮可见，无需记忆
- 快捷键 Ctrl+Shift+S 直观
- 所有操作在同一窗口内

## 详细对比

| 维度 | CLI 方案 | 扩展方案 | 优胜 |
|------|----------|----------|------|
| **发现性** | 需要阅读文档才知道有这个功能 | 状态栏按钮始终可见 | 扩展 |
| **快捷键** | 无 | Ctrl+Shift+S | 扩展 |
| **上下文切换** | 需要切换窗口到终端 | 不需要离开编辑器 | 扩展 |
| **视觉反馈** | 终端文本输出 | 通知 + 状态栏变色 | 扩展 |
| **错误处理** | 终端报错 | UI 友好的错误弹窗 | 扩展 |
| **可集成性** | 独立脚本 | 命令面板、菜单、快捷键 | 扩展 |
| **安装复杂度** | 简单 (ln -s) | 中等 (.vsix) | CLI |
| **跨 IDE 复用** | 任何终端可用 | 仅 Cursor/VSCode | CLI |
| **调试/脚本化** | 易于集成到 shell 脚本 | 需要通过 vscode 命令 | CLI |

## 场景分析

### 场景 1: 首次使用 steering

| 方案 | 用户行为 |
|------|----------|
| CLI | 用户需要先阅读文档，了解 `steer` 命令存在，然后打开终端执行 |
| 扩展 | 用户看到状态栏的 "Steer" 按钮，好奇点击，发现功能 |

**优胜: 扩展** — 零学习成本

### 场景 2: 频繁 steering（调试/迭代）

| 方案 | 用户行为 |
|------|----------|
| CLI | 保持终端窗口打开，反复输入 `steer "..."` |
| 扩展 | 反复按 Ctrl+Shift+S，输入消息，Enter |

**优胜: 扩展** — 快捷键更快，无需切换窗口

### 场景 3: 远程开发 (SSH/远程桌面)

| 方案 | 用户行为 |
|------|----------|
| CLI | SSH 到远程机器后，在远程终端执行 `steer` |
| 扩展 | 扩展在远程 VSCode 中运行，文件写入远程 |

**优胜: 平手** — 两者都可以在远程环境工作

### 场景 4: 自动化/脚本集成

| 方案 | 用户行为 |
|------|----------|
| CLI | `echo "focus on API" | steer` 或在脚本中调用 |
| 扩展 | 需要通过 `cursor --command durable-request.steer` |

**优胜: CLI** — 更易于脚本集成

## 结论

**扩展方案在日常手动使用场景中 UX 更好**:

| 指标 | CLI | 扩展 |
|------|-----|------|
| 首次使用门槛 | 高 | **低** |
| 日常使用效率 | 中 | **高** |
| 视觉反馈 | 低 | **高** |
| 脚本/自动化 | **高** | 中 |

**推荐策略: 两者都实现，优先级如下:**

1. **Phase 1 (MVP)**: 实现 CLI 方案 — 简单、可快速上线、支持自动化
2. **Phase 2 (UX 提升)**: 实现扩展方案 — 更好的日常体验
3. **长期**: 两者共存，用户根据场景选择

## 最终建议

**同时支持两种方案**，因为：

1. CLI 方案实现成本低，可快速验证 steering 功能
2. 扩展方案提供更好的日常 UX，是用户的首选入口
3. CLI 保留用于脚本化/自动化场景
4. 两者共享相同的文件协议，没有额外维护成本
